## Architecture boundary summary

Hermes Workbench is not a fork of upstream Hermes. The root compose definition keeps one upstream gateway/dashboard image isolated in Docker, mounts `workspace/` separately from `data/`, and binds dashboard port 9119 to loopback (`docker-compose.yml:2-17`). The Workbench's Vite development host proxies `/api` (including WebSockets) and `/auth` to that dashboard while exposing its own read-only workspace bridge (`src/vite.config.ts:32-107`).

The versioned Workbench boundaries are deliberately narrow:

- `HermesGatewayClient` obtains a cookie-authenticated WebSocket ticket and speaks JSON-RPC over `/api/ws` (`src/Modules/HermesGateway/HermesGatewayClient.ts:51-146`).
- Session, system/auth, model, attachment, and console adapters own their respective HTTP/WebSocket shapes (`src/Modules/HermesSessions/HermesSessionApi.ts:47-127`, `src/Modules/HermesSystem/HermesSystemAdapter.ts:148-226`, `src/Modules/HermesSettings/HermesModelAdapter.ts:114-153`, `src/Modules/HermesGateway/HermesAttachmentAdapter.ts:74-100`, `src/Modules/HermesConsole/HermesConsoleClient.ts:61-125`).
- The Windows-only desktop host adds a separate ConPTY PowerShell surface; it is not an upstream gateway replacement (`src/Host/HermesDesktop/NativeTerminalBridge.cs:3-115`).
- The full upstream dashboard remains intentionally available on loopback port 9119, including its sign-in page (`README.md:8-16`). Rows marked `upstream-delegated` remain available there rather than being copied into the Workbench.

## Compatibility-contract risks

| Risk | Concrete evidence | Failure mode | Recommended guard |
|---|---|---|---|
| Runtime identity drift | Source commit is known, but compose pulls `latest` (`docker-compose.yml:3`) and Workbench reads only a loose `version` field (`src/Modules/HermesGateway/HermesGatewayClient.ts:23-55`). | An upstream update can silently change contracts while adapters continue to claim v1. | Add a read-only compatibility preflight that records image digest/release/version and blocks or prominently degrades unsupported contract ranges. |
| Cookie + one-time WebSocket ticket boundary | Workbench mints `/api/auth/ws-ticket` and appends it to `/api/ws` (`HermesGatewayClient.ts:62-76`); upstream ticket route explicitly covers console/pty/ws/pub/events (`source/hermes_cli/dashboard_auth/routes.py:799-805`). | Proxy origin, SameSite behavior, ticket field, expiry, or query policy changes can break chat and console at once. | Treat ticket issuance + WS upgrade as a single versioned contract fixture; test protected and loopback-trusted modes. |
| JSON-RPC method/event shape drift | Workbench depends on `session.create/resume/interrupt`, `prompt.submit`, `config.*`, `approval.respond`, and named events (`useHermesChat.ts:259-388,394-435`). | Unknown/malformed events may leave the UI busy, lose tool progress, or route actions to the wrong session. | Centralize method/event schemas beside adapter version constants; replay captured success/error/unknown fixtures on every upstream bump. |

## Update-survival recommendations

1. Keep the Workbench as an adapter client of the upstream public routes/JSON-RPC boundary; do not copy upstream page, state-store, or internal UI code.
2. Replace the floating `latest` image reference with a documented update flow that records digest and tested upstream revision, while retaining explicit user-controlled update steps.
3. Make every adapter expose its own version and supported feature set. Prefer narrow capability probes and bounded 404 fallbacks over broad version-string guesses.
4. Preserve upstream dashboard delegation for security-sensitive and high-churn management pages (providers, raw config, MCP OAuth, backups, plugins, channels) until a product-approved native slice has its own API contract and tests.
5. Keep authentication cookies/tickets inside the same-origin proxy/desktop host boundary. React should receive status/identity metadata, never durable Hermes credentials or ticket values.
6. Maintain a small, replayable, non-secret compatibility corpus across each adapter. Run it after a source update and again against the exact image proposed for deployment.
